# Preflight

动手写代码前的一次**对称决策预研**：先回答「有没有现成的」，再回答「该不该做」，最后交出一个可被推翻的决策——而不是一份调研报告。

面向用 AI agent 写代码的人。核心针对两种常见病：

- **造轮子**：没查现成方案就开写。
- **单向举证**：只报收益不报成本，于是"加一丁点东西"永远看起来划算，项目就这么肿起来的。

## 装法

**项目级（团队协作推荐）** —— 跟着仓库走、进 PR、每人可按项目改参数：

```
<你的项目>/.qoder/skills/preflight/
```

**用户级（个人跨项目）**：

```
~/.qoder/skills/preflight/
```

**插件形态** —— 本仓库根目录已带 `.qoder-plugin/plugin.json`，`skills/preflight/` 是其内容。

装完 `/skills reload` 或重启会话，用 `/skills list` 确认，然后 `/preflight <一句话需求>` 手动触发，或在合适的请求上自动召回。

不提供安装脚本：装到哪个目录取决于使用者的 agent，脚本写死路径只会造成"装了但不生效"。

## 它怎么工作

主文件 `skills/preflight/SKILL.md` 里，**输出模板的顺序是固定的**，这是整套设计的关键：

```
1. 需求一句话 + 硬约束
2. 不做会怎样：最坏情况 + 严重度        ← 先写代价
3. 最强反对理由（≥2 句）                ← 反对先于支持
4. 支持理由（不许比反对更长）
5. 基线实测：体积 / 启动 / 内存 / 依赖数 ← 附命令与日期；测不了写「未测量」
6. 预估变化：与第 5 行同口径
7. 新增概念数 & 是否与现有模块职责重叠
8. 删除成本：反悔要改哪几处
9. 结论：复用 / 改造 / 自研 / 不做（四选一，不许「都可以」）
10. 翻转条件：出现什么证据就改口 + 本次明确不做的事
```

为什么这么排：先写支持理由，后面所有文字都会替它辩护；把"不做会怎样"和反对理由摆在前两位，是唯一能改变结论位置。第 5–6 行要求同口径，是为了让"成本"从需要想象的东西变成本轮可验证的数字——**给不出数字就必须写「未测量」，不许写「影响不大」**。

另有四条硬规则（决策前不写实现码、候选必须真实检索到、引入第三方需批准、淘汰要写理由）、一套契合分档（A/B/C/D，不用百分比）、以及一组带出口的停手条件。

## 可调参数

检索轮次上限 4 / 可信候选数 2 / 报告 6–10 行 / 过期天数 30。都在 SKILL.md 顶部一张表里，改完正文不受影响。

## 已知限制（v0.1.0）

- `references/metrics-baseline.md` 里的命令**只验证了工具存在，没在任何真实项目上完整跑通**。首次使用请先跑通一条再采信其余，跑不通就把该指标标「未测量」。欢迎提 issue 补其他栈的口径。
- 示例口径目前只覆盖桌面端（Rust/Tauri）与 Web 前端两张表，且明确标注为示例而非清单。
- description 以中文触发词为主，附了英文关键词；非中文环境的召回率未测。
- 工具名（WebSearch / WebFetch）取自 Qoder，其他 agent 里需替换成等价能力——但检索通道被有意设计成不押死在单个 CLI 上。

## 结构

```
preflight/
├── .qoder-plugin/plugin.json
├── LICENSE
├── README.md
└── skills/preflight/
    ├── SKILL.md
    └── references/
        ├── search-playbook.md      检索通道、种子词、排序偏差、停手与红线
        ├── metrics-baseline.md     成本口径与命令示例
        └── reporting-rules.md      状态三态 / 三种语气 / 不主动造文档
```

`reporting-rules.md` 那三条是**常设义务**，建议顺手复制进你的 `AGENTS.md`——skill 只在被触发时加载，靠 skill 承载这类规则会半数会话失效。
