# 检索打法

## 种子词

种子词 = 目标的**核心动词 + 名词**，不是整句需求。`merge pdf`、`image compress`、`global hotkey`、`tray icon`。窄词找方案，宽词找生态。

第二轮必须换词，别用同义词重复第一轮：换成实现侧术语（`pdf join`、`page append`）、相邻领域术语（`pdfium`、`mupdf`）、或语言生态前缀（`rust pdf`、`web worker upload`）。

## 层级 0：先搜自己

出门搜库之前，先在当前仓库里搜一遍，但**必须有范围和停止条件**：按顺序看 依赖清单（`Cargo.toml` / `package.json` / `pyproject.toml` 等）→ 模块入口与目录结构 → 相关符号与接口定义 → 该符号的直接调用者。命中即可停，**不得无边界遍历整个仓库**——大仓库里"再 grep 一轮"是没有上限的成本。

**命中的实现必须是活的**：有调用者、未在 deprecated 注释或废弃模块里、有对应测试或在近期改动中出现。翻到一个三年没人调用的旧实现就宣布"项目已有能力"，比造轮子更糟——它会把死代码当成架构事实复用下去。

没有读代码能力时，明确写「未检查项目现有代码」，别假装查过。

## 通道优先级

0. **`gh`（若可用）** — 先探测：`command -v gh` / `where gh`。可用则 `gh search repos "<seed>" --limit 15 --sort stars`，字段最全。
1. **网络检索工具（WebSearch 等）** — 广度。`<seed> <生态> site:github.com`、`<seed> alternatives`、`<seed> <语言/平台> library vs`。
2. **GitHub 搜索 API** — `https://api.github.com/search/repositories?q=<seed>&sort=stars&order=desc&per_page=10`，取 `stargazers_count`、`pushed_at`、`license`、`archived`。无需 token，返回 403 就是限流，改回通道 1，别重试轰炸。
3. **对应语言的包注册表页**（crates.io / npm / PyPI / pkg.go.dev / Maven Central）— 决定「加不加这个依赖」时比 GitHub 更权威：下载量曲线、版本节奏、feature 或传递依赖面。没有注册表的领域（系统组件、原生库）回到 GitHub + 官方文档。
4. **社区**（挖坑，不挖实现）：`site:reddit.com <seed> pitfalls OR "we switched"`、`site:news.ycombinator.com <seed>`、`site:lobste.rs`、v2ex。非母语社区结论只作线索，须回官方文档核对。

工具名按你所在 agent 环境替换；关键是**别把检索押在单一 CLI 上**——那台机器没装它就整条流程卡死。

## 排序偏差

只按 star 排会把「最热门」当成「最正确」，并系统性漏掉小众正解。补一轮 `sort=updated`，或搜「`<seed> minimal`」「`<seed> no dependencies`」专门找小而准的方案。体积敏感的场景里，star 高的全家桶常常是错的。

## 维护状态、契合分档、star 各有各的位子

**三件事不要压成一个权重**——star 是存量热度，会随时间累积，拿它当主判据等于自动偏向老项目：2019 年爆红如今弃管的库 8k star，2025 年每月发版的替代品 400 star。

- **维护状态是风险信号，不是自动判决。** 停更本身不构成淘汰理由——要淘汰必须写出**它在本案中造成什么具体后果**：有你需要修的未关闭缺陷；与目标平台/语言版本不兼容；API 与当前生态脱节、适配量大于自研；你需要它已经不再开发的功能。
  反过来，**停更可以是正确选择**：功能已完整覆盖需求、API 已冻结（意味着不会变坏）、无已知 CVE、你不需要新特性 —— 这时结论写「承担后果：出问题自己修」即可。只有"它很久没提交"这一条，不足以淘汰。
  用统一词表描述状态，每个状态都要给证据：
  | 状态 | 判定证据 |
  |---|---|
  | Active | 近 12 个月有提交或 release；issue/PR 有人回应（非机器人模板） |
  | Slow | 维护迹象在但节奏低：12–24 个月内有提交，或 issue 有人回但长期无 release |
  | Successor | **有明确指向**：原仓库 README/官方公告指向新仓库，或原作者另起项目。缺一不可 |
  | Community Continuation | 有活跃提交与独立 release，但无官方指向 —— 只能说「社区接管版」 |
  | Legacy | 停更，但功能仍可用、仍被广泛依赖 |
  | Abandoned | 停更且未发现任何继续维护版本 |
  | Unknown | 抓不到 `pushed_at`/release 等字段，或来源互相矛盾。**宁可写 Unknown 也不猜** |
- **分档**：对本项目需求的契合度 A/B/C，见 SKILL.md。
- **排序**：star、下载量、被多少活跃项目依赖 —— star **只是历史社区关注度信号**，它既不能证明当前质量，也不能证明有人在用（判断采用度请用下载量与反向依赖数）。不许因为它改变已经给出的技术、维护或兼容结论；真实世界里"其他条件基本相当"几乎从不成立，所以这句话就是堵那个口子：只有逐项都能写出"相同"时，才允许用它做选择。

不许把这几项加权成一个分数（`star 40% + 维护 30% + …= 87.3`）：权重无法客观确定，算出来的数字只会把判断藏进算术里。摆事实，说差异。

表述带时间点：说「截至本次检查，最近一次 release 为 __」，不说「这项目已经没人维护了」；证据不足说「未确认」。

## 原版停更时的替代顺序

1. **同一 org 的后继项目**（改名、重写、官方迁移公告指向的新仓库）——血统最干净。
2. **提交更近的活跃 fork**，即使 star 少于原版。继续维护几乎总优于等人接手；但要标成「社区接管版」，并先查它**是否改动了公共 API、feature 名、MSRV**。
3. **只抄接口，实现自研**：停更的成熟库常见形态是「设计值得抄，代码不值得背」。

**fork 不等于继任者。** 除非满足词表里 Successor 的证据（原仓库 README 或官方公告明确指向），就只能写「存在活跃 fork，但无法确认其为官方继任项目」。把 fork 说成 successor 会让人以为可以沿用原版的文档与 API —— 恰恰是最容易踩空的地方。

**头号陷阱：选了 fork 却照原版的文档写代码。** fork 往往已改过签名与 feature 门，而模型存的是原版知识，于是问题到编译期才暴露。用了 fork 就必须重读**该 fork 的** README 与 feature 列表。

## 时间戳记的是来源，不是你抓取的当天

抓到页面不等于内容最新。记录**来源自身的时间线索**：`pushed_at`、最新 release 标签、页面标注的 last-updated。README 写着「支持 v2」而仓库停在 v1 的情况不少见——两类日期都要，冲突时以 commit/release 为准。

判断依据是**相对变化速率**，不是绝对新旧：一个月前还在发版的高频项目可能已改过三次 API，五年没动的单一职责库可能一行都不用改。所以新鲜度用来决定**该不该去查**，不用来决定**该不该选**。

## 可信候选的最低标准

进结论的候选至少要有：可点开的仓库 URL、最近一次提交时间、许可证、以及它覆盖需求的哪几条。缺任一项就标「未核实」，不许用它支撑决策。

## 停手

满足任一即停（轮次上限见 SKILL.md 可调参数）：

- 已有足够可信候选（默认 2 个）且分档能拉开差距
- 连续 2 轮零有效结果 —— 这是空白区，本身就是有价值的结论，直接进自研分支
- 选中候选已停更，且继任者/接管版检查做完一轮（结果写进输出第 9 行，允许是「未发现」）
- 到达轮次上限 —— 把中间结论交给人，比继续搜索更有价值

## 红线

- 不把搜索引擎摘要当作已验证事实；引用的数字（星数、下载量、版本号）必须来自实际抓到的页面。
- 不引入破解、注册机、逆向绕过类方案，即使来源是技术论坛。
- 论坛片段不照抄进代码；只把「坑」转写成一条能复现的测试或一句解释为什么的注释。
- 引用外部内容注明来源，不复制成自己的产出。
