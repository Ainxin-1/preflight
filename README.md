# Preflight

动手写代码前的一次**对称决策预研**：先回答「有没有现成的」，再回答「该不该做」，最后交出一个可被推翻的决策——而不是一份调研报告。

面向用 AI agent 写代码的人。核心针对两种常见病：

- **造轮子**：没查现成方案就开写。
- **单向举证**：只报收益不报成本，于是"加一丁点东西"永远看起来划算，项目就这么肿起来的。

## 装法

核心规则与具体 agent 无关，各环境路径见 **[`adapters/README.md`](adapters/README.md)**。最短版：把 `skills/preflight/` 整目录放进你的 agent 实际扫描的技能目录，然后确认技能列表里能看到 `preflight`。

不提供安装脚本：装到哪儿取决于使用者的 agent，脚本写死路径只会造成「装了但不生效」。

## 它怎么工作

主文件 `skills/preflight/SKILL.md` 里，**输出模板的顺序是固定的**，这是整套设计的关键：

```
1. 需求一句话 + 硬约束
2. 不做会怎样：最坏情况 + 严重度        ← 先写代价
3. 最强反对理由（≥2 句）                ← 反对先于支持
4. 支持理由（不许比反对更长）
5. 基线实测：体积 / 启动 / 内存 / 依赖数 ← 附命令与日期；测不了写「未测量」
6. 预估变化：与第 5 行同口径
7. 新增概念数 & 是否与现有模块职责重叠
8. 删除成本：反悔要改哪几处
9. （仅当候选停更时）停更检查：原项目状态 → 有无继任/接管版 → 继任关系可确认吗
10. 结论：复用 / 组合 / 改造 / 自研 / 不做 / 暂缓（六选一，不许「都可以」）
11. 翻转条件：出现什么证据就改口 + 本次明确不做的事
```

为什么这么排：先写支持理由，后面所有文字都会替它辩护；把"不做会怎样"和反对理由摆在前两位，是唯一能改变结论位置。第 5–6 行要求同口径，是为了让"成本"从需要想象的东西变成本轮可验证的数字——**给不出数字就必须写「未测量」，不许写「影响不大」**。

另有五条硬规则（决策前不写实现码、候选必须真实检索到、引入第三方需批准、淘汰要写理由且**硬约束一票否决不许用 star 补分**、高时间敏感断言不许用现在时陈述且**内外证据冲突必须留痕**），一套契合分档（A/B/C/D，不用百分比），一组带出口的停手条件。三条结构性设计：

- **默认 Light，命中清单才升 Deep。** 模式判定不交给"觉得复不复杂"——那种判断必然倒向省事；改成命中任一即 Deep 的清单（引新依赖、动认证/加密/权限、换存储或网络或框架、多方案竞争、带来长期维护面）。
- **层级 0：先搜自己。** 找现成方案的顺序是「标准/协议 → 语言标准库 → OS 原生能力 → **当前项目已有代码与已有依赖** → SDK → 框架 → 第三方库 → 开源项目 → 自研」，由便宜到贵。「现成方案」不等于"第三方库"——最省的那个常常已经在你仓库里。
- **维护状态是风险信号，不是自动判决；契合度是分档；star 只是历史社区关注度信号，既证明不了当前质量也证明不了用户在用**（要判断采用度看下载量与被依赖数），更不能翻掉已给出的技术/维护/兼容结论；且禁止把三者加权成一个分数（`star 40% + 维护 30% = 87.3` 这类假精确）。**光"很久没提交"不能淘汰一个候选**——要淘汰得说出它在本案中造成什么具体后果；功能已覆盖需求、API 已冻结、无已知 CVE 的停更库往往是对的选择（结论写清"出问题自己修"）。候选用统一状态词表描述（Active / Slow / Successor / Community Continuation / Legacy / Abandoned / Unknown），每个状态都要给证据，且**每个候选只写两行**：来源·状态·最新活动·许可证·覆盖需求第几条 ／ 主要问题与成本。原版停更时按「同 org 后继 → 活跃 fork → 只抄接口」找替代，并警惕两件事：**fork 不等于继任者**（无官方指向证据只能说"社区接管版"），以及**用了 fork 却照原版文档写代码**。

## 可调参数

检索轮次上限 4 / 可信候选数 2 / 候选上限 Light 3、Deep 4 / 报告长度 每项 ≤2 行、Light ≤8 行、Deep ≤20 行 / 过期天数 30。都在 SKILL.md 顶部一张表里，改完正文不受影响。

## 已知限制（v0.5.0）

- v0.5.0 的六处修补来自一次**外部评审**（把规则摘要交给另一个模型独立挑洞）。采纳：层级 0 需要范围与停止条件、"真实检索"要防套壳、反对理由要防模板化空话、授权可来自宿主已有权限、硬约束否决的对象是最终方案而非组件、star 不得翻掉已有结论。**拒绝**了它的两副药：把"行"改成"条目"（会让限长直接空转）、给 Light/Deep 加"命中但其实没风险"的降级出口（不可核查，等于把判断交回模型自觉）。
- `adapters/README.md` 里只有 Qoder 的路径经过验证，其他 agent 一律标未验证——不是懒得写，是没证据。
- 曾有提案把输出改成字段更多的"决策卡片"（含知识新鲜度高中低、把反对理由放到决策之后）。**已明确拒绝**：卡片一旦放宽，实测数字、删除成本、职责重叠这三格基本会空着，而"反对先于支持"的顺序一旦颠倒，整份输出就变成替决策辩护。要加字段请先说明它替换掉现有哪一行。

- `references/metrics-baseline.md`：**移动端口径已在 Android 17 真机核对**（`dumpsys meminfo` 字段名、`pm path` + `ls -l` 取 apk 体积，2026-09-20；冷启动仍未验，因为它会把应用拉到用户前台）。**桌面端与 Web 两表仍只验证了工具存在，没跑通完整流程**。首次使用先跑通一条再采信其余，跑不通就把该指标标「未测量」。欢迎提 issue 补其他栈的口径。
- 示例口径目前只覆盖桌面端（Rust/Tauri）与 Web 前端两张表，且明确标注为示例而非清单。
- 整套流程**尚未在任何真实需求上完整走过一轮**：层级 0、维护状态词表、停更检查、Light/Deep 升级清单这四处新加的判据尤其需要实战检验——升级清单可能偏松（该 Deep 的没升）也可能偏紧（小改动被拖成完整预研）。
- description 以中文触发词为主，附了英文关键词；非中文环境的召回率未测。
- 核心规则只描述能力（"有外部检索就验证，没有就标未验证"），具体通道名写在 `references/search-playbook.md` 里按环境挑用——刻意保留这些具体性：抽象措辞的执行力明显低于具体命令，而绑死某个 CLI 会让没装它的机器整条流程卡死。分层是为了两头都不丢。

## 结构

```
preflight/
├── .qoder-plugin/plugin.json       Qoder 打包清单（可选，其他 agent 忽略）
├── LICENSE
├── README.md
├── adapters/
│   └── README.md                   各 agent 的安装方式；核心规则不依赖它
└── skills/preflight/               ← 核心，拷走这个目录就能用
    ├── SKILL.md
    └── references/
        ├── search-playbook.md      检索通道、种子词、维护状态词表、停手与红线
        ├── metrics-baseline.md     成本口径与命令示例
        └── reporting-rules.md      状态三态 / 三种语气 / 不主动造文档
```

`reporting-rules.md` 那三条是**常设义务**，建议顺手复制进你的 `AGENTS.md`——skill 只在被触发时加载，靠 skill 承载这类规则会半数会话失效。
